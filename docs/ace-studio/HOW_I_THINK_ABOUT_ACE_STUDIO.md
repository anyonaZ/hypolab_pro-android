# How I think about ACE Studio

I built ACE Studio for myself and other WorldQuant BRAIN consultants because research often becomes fragmented. I can discover a promising dataset, form an idea, write expressions, run simulations, and later struggle to reconstruct why I tested a particular formula or what its failure taught me. ACE Studio connects those steps into one research memory.

For a BRAIN team presentation, I would describe it as a local research automation workspace around each consultant's own account. The aim is not to automate judgment away. It is to automate repetitive retrieval, grounding, validation, simulation, and record keeping so that more of our time goes into economic reasoning and learning from evidence.

Each user brings their own BRAIN session and AI provider keys. The application runs locally with a React interface, a Python FastAPI backend, and a SQLite research database. It talks to BRAIN for account-specific options, datasets, fields, operators, alphas, and simulations. It sends selected research context to the AI provider configured by the user. The local database retains datasets, hypotheses, prompts, expressions, and results so the research trail survives beyond one session.

The automated loop begins with data because field availability is a hard constraint. Data Explorer loads the actual region, universe, delay, datasets, and datafields available to the account. It keeps full field descriptions and types throughout prompting. MATRIX and VECTOR fields have different expression requirements, and validating those requirements early prevents the model from inventing identifiers or producing structurally impossible formulas.

I also built a user-directed local data catalog because repeatedly fetching the same metadata wastes account requests and leaves later algorithms without memory. I can choose instruments, regions, delays, universes, categories, coverage and value thresholds, review the number of valid contexts, set a hard request ceiling, and fetch dataset metadata alone or include every field. Each concept is stored once in SQLite while its availability is recorded separately for every instrument, region, delay and universe. Syncs survive restarts as resumable plans, support missing-only and stale-only refreshes, and can be exported or restored as a local JSON backup. Ordinary Data Explorer browsing also enriches this catalog, so it improves gradually without requiring a full account scan.

That catalog is useful beyond faster browsing. Selecting a catalogued dataset can reveal its saved fields immediately, without another metadata request. Hypotheses can be matched against full field descriptions, related fields can be found inside a dataset or through description similarity, and D0/D1 and cross-region intersections are explicit. This gives future knowledge algorithms a persistent dataset-to-field graph while keeping BRAIN as the authority for current availability, proprietary observations and simulation results.

The next layer is hypothesis formation. The model is asked for a mechanism, expected sign, horizon, falsification test, and data requirements before it is asked for code. This separation matters. A useful thesis should not disappear because the model made a syntax mistake in an illustrative expression. A hypothesis can be grounded in currently selected data, or it can be saved as a general mechanism and rebound to suitable fields later.

Saved hypotheses form a reusable research library. They are stored uniquely by their core semantic content, together with their original context. I can reuse one to curate a generation prompt for another eligible region or dataset, or explore different operator families while keeping the economic thesis fixed. This creates a cleaner experimental comparison: the mechanism stays stable while the implementation changes.

Alpha Lab also supports learning from an existing BRAIN alpha by ID. The studio fetches its code from the user's account and asks the model to separate the durable economic mechanism from the exact fields, windows, and operators. It then checks whether the selected target fields actually measure what that mechanism needs. The prompt explicitly rejects blind field substitution, timing leakage, redundant inputs, arbitrary sign changes, and complexity added only to fit history. The result is a set of falsifiable transfer hypotheses, not a promise that an old formula will work on unrelated data.

Generation compiles hypotheses into FastExpr candidates using only the selected fields and the account's operator catalogue. Operator signatures and examples come from Operator Atlas. The model may use up to the chosen operator budget and is encouraged to use fewer when the mechanism is simple. Coverage across datasets and operator families is balanced where it makes economic sense rather than enforced as a quota. Candidates then pass deterministic field, type, arity, syntax, and complexity checks, repair passes, deduplication, and an economic-sense review before they are offered for simulation.

Template Studio approaches the same problem from structure rather than prose. A useful expression shape can become a parameterized template, be expanded across compatible fields, reshuffled through alternative transformations, and validated before simulation. Prompt Library retains reusable generation instructions with dataset context. Strategy Lab helps reason about a field or combination before generation. Operator Atlas preserves correct signatures, examples, and my own notes. Together these components turn successful research patterns into reusable knowledge without treating a past winner as universally valid.

Evolution Lab gives me a controlled way to explore variations after I already have an expression worth investigating. It starts empty, so an old run cannot silently steer a new experiment. I paste seeds myself or deliberately send them from Alpha Lab or Template Studio. For a two-field expression I can preserve the exact pair, substitute only from my explicit selection, expand inside the same datasets, or explore locally catalogued fields from the same categories. That covers same-dataset pairs, different datasets measuring one category, and controlled two-category relationships without allowing the engine to introduce a third category. I choose any combination of horizon, field, operator, normalization, smoothing, difference, sign, group, simplification and crossover mutations. Operator exploration is grounded in my own Operator Atlas rather than a short built-in list: the run snapshots its signatures, spreads candidates across time-series, cross-sectional, group, vector, arithmetic, logical, regression, turnover-control and transform families, supplies required inputs, varies selected lookbacks and supported keyword parameters, and validates every result. I set a unique-candidate target and see the maximum BRAIN cost before running. The evolutionary search itself needs no LLM. It uses a saved random seed, canonical expression identity, typed validation, pilot simulations, Pareto selection and promotion of only the stronger candidates to additional configurations. A permanent expression ledger shows every evaluated descendant, its parent, exact mutation, stage, complexity and evidence, so I can follow what the algorithm actually did. I can reproduce the same generated population and send chosen survivors to Simulation. This is a disciplined sensitivity and robustness experiment around a research idea, not a machine for declaring whichever formula wins an in-sample tournament to be true.

Simulation is where every claim meets BRAIN. The studio supports batches, settings, concurrency, tags, and parameter or universe sweeps. Work runs in background threads so navigation does not cancel it, although jobs currently live in process memory and do not survive a backend shutdown. Results & Analytics explains which metrics passed or failed and compares candidates. Correlation & Portfolio uses downloaded PnL to find compatible groups under a selected correlation threshold and can run a separate production-correlation check.

The studio's result gate is an internal research filter. Its current defaults require absolute Sharpe of 2.69 and Fitness of 1.5 for delay zero, or 1.58 and 1.0 otherwise, turnover below 0.70, and no reported in-sample failures. Correlation checks apply when that path is enabled. Passing this gate means a result deserves attention under the configured rules; it does not guarantee that BRAIN will accept a submission.

SuperAlpha remains separate because combining existing alphas has a different vocabulary and risk profile from building a regular expression from datafields. It has dedicated selection and combination operators, validation, previews, and simulation handling. Keeping those concepts separate reduces accidental misuse while allowing the evidence from both workflows to live in the same studio.

The system is local, but distribution is automated. Source users can receive a clean package whose launcher checks my configured update URL while preserving local research state and local distribution tokens. Executable users receive a PyInstaller folder that includes the backend, frontend, and runtime dependencies. Signed release manifests let the updater verify origin and integrity before replacing an installation. The update token and support token are distribution credentials and remain readable to recipients; personal BRAIN sessions, AI keys, signing keys, databases, and caches must never be packaged.

When no BRAIN session exists, the workspace is locked behind the login screen. That prevents a user from building research against stale or generic assumptions when their real regions, fields, and operators are unavailable. The executable can be used from any location; BRAIN account permissions determine the research regions available to each user.

The value I want ACE Studio to create for WorldQuant is a more disciplined research cycle:

1. Discover what data is genuinely available.
2. State an economic mechanism and how it could be falsified.
3. Bind that thesis to fields whose descriptions support it.
4. Generate several controlled implementations instead of one overfit formula.
5. Reject structural and economic mistakes before spending simulation capacity.
6. Compare results, robustness, and correlation evidence.
7. Save the hypothesis, prompt, implementation, and outcome so the next experiment starts from accumulated knowledge.

The strongest automation here is the continuity between these stages. A dataset selection becomes hypothesis context; a hypothesis becomes a constrained generation prompt; valid expressions become simulation jobs; results update the local research history; and that history influences what the studio suggests next. I designed the system to help a consultant run more careful experiments, preserve the reasoning behind them, and develop a distinct research direction with less repetitive work.
